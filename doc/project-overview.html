ระบบตารางเรียนอัตโนมัติ

เว็บสำหรับสถานศึกษาไทย อ่านไฟล์หลักสูตร (PDF) ให้หัวหน้าแผนกกับครูวางแผนภาคเรียนร่วมกัน แล้วสร้างตารางที่ไม่มีคาบชนกันให้ตรวจ แก้ และพิมพ์ได้ เริ่มจากอาชีวศึกษา (ปวช./ปวส.) เป็นโอเพนซอร์ส แต่ละสถาบันติดตั้งบนเซิร์ฟเวอร์ของตัวเอง

ปัญหาผู้ใช้9 ขั้นตอนสถาปัตยกรรมTech stackโครงสร้าง Frontendข้อมูลสถานะวิธีรัน
4บทบาท: ADMIN, HEAD, ASSISTANT, TEACHER
9ขั้นตอนในพื้นที่ทำงานของโปรไฟล์ตาราง
17เส้นทาง (route) ในหน้าเว็บ
≈7,000บรรทัดโค้ด TypeScript/TSX (ไม่รวม test)
187test ผ่านทั้งหมด ใน 35 ไฟล์
36ตารางใน schema Supabase พร้อม RLS
62/63คะแนนที่วัดได้ของ backend ตามเกณฑ์การแข่งขัน
0คาบชนกันในทุกเคสทดสอบ (placed ครบ)

ตัวเลขนับจากโค้ดและผลรันจริงของวันที่เขียนเอกสาร ไม่ใช่ตัวเลขประมาณการ

ปัญหาที่แก้

สถานศึกษาส่วนใหญ่จัดตารางเรียนด้วยมือใน Excel และกระดาษ ใช้เวลา 3 วันถึง 1 สัปดาห์ต่อภาคเรียน และตรวจการชนของครู ห้อง และกลุ่มเรียนด้วยสายตา ระบบนี้เปลี่ยนงานนั้นเป็นลำดับที่ตรวจย้อนได้:

อ่านหลักสูตรได้เอง

อ่านข้อความและไฟล์สแกน (OCR) ให้คะแนนทุกแถววิชาเป็น ✓ ⚠ ✗ ? พร้อมเหตุผล ให้คนแก้เฉพาะที่สงสัย และบอกหน้า PDF ที่มา

จัดตารางไม่ให้ชน

ใช้ solver FET จัดตาม กฎบังคับ (hard) และกฎที่ควรทำ (soft) ครู ห้อง และกลุ่มเรียนต้องไม่ซ้อนเวลา

ทุกการแก้มีบันทึก

ตารางที่เผยแพร่แล้วล็อก การแก้ภายหลังสร้างเวอร์ชันใหม่ และเก็บว่าใคร เปลี่ยนอะไร ตกลงกับใคร

นักเรียนไม่ต้องล็อกอิน

ตารางที่เผยแพร่แล้วเปิดดู/พิมพ์ได้แบบอ่านอย่างเดียว ไม่มีข้อมูลนักเรียนในระบบ

ผู้ใช้และสิทธิ์

บทบาทใครเป็นทำอะไรได้
ADMINผู้ดูแลสถาบัน (ตั้งค่าครั้งแรกตอนติดตั้ง)สร้างแผนก เชิญหัวหน้า ห้องร่วม ปฏิทินภาคเรียน อนุมัติรูปแบบหลักสูตร โอนสิทธิ์ผู้ดูแล
HEADหัวหน้าแผนก (ผู้ใช้หลัก)ทำขั้น 1-9 ได้ทั้งหมด เป็นคนเดียวที่เผยแพร่ตารางได้ เชิญผู้ช่วยและครู
ASSISTANTผู้ช่วยหัวหน้าทำขั้น 1-8 เชิญครูได้ แต่เผยแพร่ไม่ได้
TEACHERครู/อาจารย์ส่งเวลาว่าง จัดอันดับวิชา ดูตารางของตัวเอง ยื่นขอเปลี่ยนคาบ
นักเรียนไม่ใช่ผู้ใช้ดูตารางที่เผยแพร่แล้ว (อ่านอย่างเดียว ไม่ล็อกอิน)

คนเดียวสังกัดได้หลายแผนกและมีหลายบทบาท (เช่น หัวหน้าที่หนึ่ง ครูอีกที่) โดย ADMIN เป็นสิทธิ์ระดับสถาบัน (user.is_admin) ไม่ใช่สมาชิกแผนก ไม่มี SMTP: การรีเซ็ตรหัสผ่านและคำเชิญใช้ลิงก์ที่ผู้ดูแลหรือหัวหน้าคัดลอกส่งเอง

เส้นทางการทำงาน 9 ขั้นตอน

หัวหน้าแผนกทำงานเป็นลำดับในพื้นที่ทำงานของโปรไฟล์ (หนึ่งโปรไฟล์ต่อแผนกต่อภาคเรียน) ขั้นถัดไปปลดล็อกเมื่อขั้นก่อนเสร็จ ถ้าย้อนไปแก้ขั้นเก่า ขั้นหลังที่เสร็จแล้วของ year plan นั้นจะกลายเป็น "ล้าสมัย"

  1. ตั้งค่าหลักสูตร × ชั้นปี
  2. ตรวจข้อมูลแถวที่ระบบสงสัย + หน้า PDF
  3. รอบเวลาว่างเปิดรอบให้ครูกรอก
  4. ข้อมูลอาจารย์ปัญหา BLOCKER / WARNING
  5. กฎ + วิชาเลือกhard / soft + น้ำหนัก
  6. สร้าง + จัดตารางprecheck แล้วรัน solver
  7. ห้อง + อาจารย์กำหนดห้อง ตรวจชน
  8. อาจารย์ตรวจทานขอเปลี่ยน อนุมัติ
  9. เผยแพร่ + พิมพ์เฉพาะ HEAD

สถานะโปรไฟล์: draft → review → published (เผยแพร่แล้วล็อก แก้ต้องสร้างเวอร์ชันใหม่)

สถาปัตยกรรมซอฟต์แวร์

ระบบแยกเป็นสามส่วน เบราว์เซอร์ (React) ฐานข้อมูล (Supabase/PostgreSQL) และบริการอ่านหลักสูตร + จัดตารางบน Docker ตอนนี้หน้าเว็บทำงานบน mock API ที่เก็บสถานะลง Supabase แบบ snapshot ส่วนที่ต่อเสร็จจริงคือการอ่านหลักสูตร (ขั้น ①) ผ่านพร็อกซี /api

ใช้งานอยู่ (ส่วนของเรา)Backend (ฝั่งอานนท์)วางแผนหรือยังไม่ต่อ

หลักการที่ตัดสินใจแล้ว

  • หน้าเว็บ ไม่คุยกับ solver ตรง ทุกอย่างผ่านบริการกลางตัวเดียวที่เป็นผู้เขียนข้อมูลและบันทึกทุกการเปลี่ยน
  • สิทธิ์ที่ซ่อนใน UI เป็นแค่ความสะดวก ตัวจริงบังคับที่ฐานข้อมูล (RLS และ trigger)
  • รูปแบบหลักสูตรเป็นข้อมูล ไม่ฝังในโค้ด เพื่อรองรับประเภทสถานศึกษาอื่นภายหลัง
  • ใช้ hash router (#/people) เพื่อ host เป็นไฟล์สถิตหลัง nginx ได้โดยไม่ตั้ง rewrite

กติกาข้อมูลที่ห้ามผิด (ตัวอย่าง)

  • ตารางที่เผยแพร่แล้วไม่มีครู ห้อง หรือกลุ่มเรียนซ้อนเวลา
  • หนึ่งโปรไฟล์ต่อแผนกต่อภาคเรียน
  • เวลาว่างผูกกับ คน × ภาคเรียน ใช้ร่วมทุกแผน
  • รัน solver ได้เมื่อรับทราบรายงานตรวจก่อนรันแล้ว
  • ปิดปัญหาได้ด้วยการตัดสินใจเท่านั้น
  • ไฟล์หลักสูตรต้นฉบับห้ามแก้ การแก้ทำที่แถววิชา

สถานะปัจจุบัน

ทำเสร็จและใช้งานได้

  • หน้าเว็บครบทุกบทบาทบน mock API: ล็อกอิน ตั้งค่าครั้งแรก คำเชิญ รีเซ็ตรหัสผ่าน บัญชีของฉัน บุคลากรและห้อง โครงสร้างสถาบัน ปฏิทินภาคเรียน โปรไฟล์ พื้นที่ทำงาน 9 ขั้น เวลาว่างของครู ปัญหา การขอเปลี่ยนคาบ แจ้งเตือน
  • ข้อมูลส่วนตัว (ตำแหน่ง ช่องทางติดต่อ ห้องทำงาน) และรายละเอียดห้อง (หลายรูป อุปกรณ์ คำอธิบาย)
  • ตั้งค่าหน้าตา: ธีม สีหลัก ขนาดอักษร ความหนาแน่น มุม
  • Backend อ่านหลักสูตรไทย (รวมไฟล์สแกน) และจัดตารางได้ ผลทดสอบ 5 เคส (เล็กถึงใหญ่) วางครบทุกคาบ ไม่ชน อ่านถูก 99-100% ในไฟล์ที่มีเฉลย และไม่มีค่าผิดแบบเงียบ
  • Schema ฐานข้อมูลเชิงสัมพันธ์ ทดสอบการบังคับกฎและสิทธิ์แล้ว

ยังไม่ได้ทำ

  • ต่อหน้าเว็บกับ API จริงครบทุกขั้น (ตอนนี้ต่อเฉพาะขั้น ① อ่านหลักสูตร)
  • ย้ายข้อมูลจากตาราง kv ไปตารางเชิงสัมพันธ์ และใช้ Supabase Auth แทนบัญชี mock
  • ที่เก็บรูปและไฟล์จริง (ตอนนี้รูปเป็น data URL)
  • พิมพ์ตาราง A4 และส่งออก PDF/Excel
  • ลากวางคาบในตาราง สลับภาษาไทย/อังกฤษ
  • รองรับอุดมศึกษาและการศึกษาขั้นพื้นฐาน (หน้าล็อกอินแสดงเป็นแผนงาน)
  • เปิดให้ใช้ออนไลน์ (ยังไม่เลือก host)
ข้อควรระวังสำหรับผู้อ่านเอกสารเก่า เอกสารใน doc/dev/ บางไฟล์ (เช่น ROADMAP และ tech stack) เขียนตอนโค้ดยังเป็น JavaScript ประมาณ 470 บรรทัด ปัจจุบันเป็น TypeScript เกือบ 7,000 บรรทัดและมี test แล้ว ถ้าตัวเลขหรือเครื่องมือในเอกสารเก่าขัดกับหน้านี้ ให้ยึดหน้านี้และโค้ดจริง

วิธีรัน

Frontend

cd frontend
npm install
npm run dev          # เปิดที่ localhost

# ตรวจก่อนส่งงาน
npm run typecheck && npm run lint && npm test && npm run build

ต้องตั้ง VITE_SUPABASE_URL และ VITE_SUPABASE_PUBLISHABLE_KEY ใน frontend/.env (ดูตัวอย่างใน .env.example) ถ้าติดต่อ Supabase ไม่ได้ จะใช้ข้อมูล mock ในเครื่อง

Backend

cd backend
docker compose up --build        # http://127.0.0.1:8080
docker compose run --rm rubric   # รันชุดทดสอบตามเกณฑ์ ~1 นาที

Vite พร็อกซี /api ไปพอร์ต 8080 จึงต้องเปิด backend ก่อนใช้ขั้นอ่านหลักสูตร

ฐานข้อมูล

รัน frontend/supabase/schema.sql ใน Supabase SQL editor ทั้งไฟล์ รันซ้ำได้
